Engineering Leadership Review

The Problem We're Solving

Two worlds, two cost centers

  • Batch analytics: dbt + warehouse. Great ergonomics, hours-stale data.
  • Streaming: Flink/Kafka. Millisecond freshness, opaque jobs, no lineage.
  • Same metrics computed twice, prayed to agree.

What leadership keeps asking

  • Why don't the live and historical numbers match?
  • Who owns this Kafka topic? What depends on it?
  • Why does every new metric need a Java engineer?
  • Can we tell what changed between yesterday and today?

→ The lambda architecture tax is real: 2× pipelines, 2× teams, 2× drift.

Thesis

Combine Flink's streaming engine with dbt's SQL governance layer to deliver real-time freshness with batch-analytics ergonomics — one definition, one DAG, latency picked per model.

Data Flow — A Single Order

  1. OLTP write → row inserted in Postgres
  2. CDC capture → Debezium emits change event to MSK topic orders_topic
  3. Flink SQL job consumes Kafka, writes append-only event to Iceberg iceberg_orders_cdc_log
  4. dbt model mart_orders_cdc_current projects "current state" via ROW_NUMBER() OVER (PARTITION BY id ORDER BY event_ts DESC)
  5. BI query reads the dbt view → sees the new order seconds after the OLTP write

End-to-end p95: ~5–10 seconds. No batch window, no lambda drift, no second pipeline.

The CDC Pattern — Append-Only + Projection

Why append-only?

  • Iceberg streaming writes work best as inserts
  • Full history retained — time travel for free
  • No row-level locks, no MERGE contention
  • Replays are deterministic

Why project at read?

  • "Current state" is just a window function
  • Soft deletes = WHERE op <> 'DELETE'
  • Schema evolves without rewrites
  • Same log feeds many downstream marts
-- mart_orders_cdc_current.sql  (5 lines)
{{ config(materialized='view') }}
{{ cdc_current_state(
    source_table="iceberg_catalog.`default`.iceberg_orders_cdc_log",
    key_columns=['id'],
    extra_columns=['customer_id', 'order_ts', 'amount', 'status']
) }}

Code Minimization via dbt Macros

One reusable macro replaces dozens of hand-written CDC projections.

{% macro cdc_current_state(source_table, key_columns, extra_columns,
                            order_column='event_ts',
                            op_column='op', delete_value='DELETE') %}
SELECT {{ key_columns | join(', ') }}, {{ extra_columns | join(', ') }},
       {{ op_column }} AS operation, {{ order_column }} AS last_modified_at
FROM (
  SELECT {{ key_columns | join(', ') }}, {{ extra_columns | join(', ') }},
         {{ op_column }}, {{ order_column }},
         ROW_NUMBER() OVER (PARTITION BY {{ key_columns | join(', ') }}
                            ORDER BY {{ order_column }} DESC) AS rn
  FROM {{ source_table }}
  WHERE {{ op_column }} <> '{{ delete_value }}'
)
WHERE rn = 1
{% endmacro %}

Adding a new CDC table = one 5-line model file. No SQL duplication, no drift.

Complex Problems This Architecture Solves

1. Lambda death

Same SQL runs as a Flink streaming job and a batch backfill. One source of truth.

2. Streaming governance

dbt docs shows lineage from Kafka topic → Iceberg → mart. Tests run on streams.

3. CDC at scale

Soft deletes, late data, dedup, SCD2 — all declarative via macros instead of bespoke jobs.

4. ML feature parity

One feature definition serves both training (batch over Iceberg) and serving (streaming output).

5. Schema contracts

dbt tests + freshness checks block deploys when an upstream Kafka schema change breaks downstream.

6. SQL-fluent ownership

Analytics engineers own streaming pipelines. No Java, no Flink job submitter scripts.

dbt as Deployment Layer for Streaming

Mental model shift: dbt doesn't execute streams — it deploys them.

-- A streaming dbt model
{{ config(
    materialized='table',
    execution_mode='streaming'
) }}
SELECT
  o.id,
  o.customer_id,
  o.amount,
  c.tier AS customer_tier,
  o.amount * c.tier_multiplier AS adjusted_amount
FROM {{ source('kafka', 'orders_topic') }}  o
LEFT JOIN {{ ref('dim_customers') }}        c
  ON o.customer_id = c.id
  • dbt run issues INSERT INTO sink SELECT ... via Flink SQL Gateway
  • Flink picks it up as an unbounded job — runs forever
  • Re-deploys are version-controlled SQL changes, not Java repackages

Tradeoffs — What You Should Know

  • ⚠ dbt-flink-adapter is community-maintained and version-locked (1.3.x). Less mature than dbt-snowflake/bigquery.
  • ⚠ Streaming semantics still leak: watermarks, state TTL, checkpoints, exactly-once — Flink expertise still required.
  • ⚠ dbt deploys, doesn't operate. Streaming jobs need separate lifecycle tooling (restart policies, monitoring, version checks).
  • ⚠ Iceberg + streaming writes create small files — periodic compaction job is non-optional.
  • ⚠ Some dbt features don't translate (snapshots, exposures, freshness on streams have rough edges).
  • ✓ None of these are blockers — they're known operational gaps with known patterns.

When NOT to Use This Stack

Skip if…

  • 15-minute batch latency is acceptable everywhere
  • Team is Java-fluent and already owns Flink jobs
  • Volume < 1M events/day (overkill)
  • You don't already use dbt

Wins clearly if…

  • SQL-fluent analytics team owns the pipeline
  • Real-time needed selectively, not everywhere
  • You want one DAG across batch + streaming
  • CDC ingestion is on the roadmap
  • Lakehouse / Iceberg is already the storage choice

Key Takeaways

  1. One DAG spans batch and streaming — no lambda drift.
  2. SQL-first — analytics engineers own real-time pipelines.
  3. Latency per model — view, incremental, or streaming, all in one project.
  4. CDC done right — append-only logs + macro projections, no MERGE pain.
  5. Governance for streams — dbt lineage, tests, docs, contracts.
  6. Operational gaps exist — known and addressable, not blockers.
