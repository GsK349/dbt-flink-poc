Mental model — three planes

  • Streaming plane writes append-only logs. Always-on.
  • Transform plane projects current state. Scheduled (15 min).
  • Storage plane is the source of truth read by everyone.

Trace one record — INSERT for order id=1001

  1. App writes to OLTP → Postgres row inserted
  2. Debezium emits Kafka event to orders_topic
    Headers: {operation: INSERT, source: order-service, timestamp: ...}
    Body: {id: "1001", customer_id: "cust_1001", amount: 15.50, status: "created"}
  3. Flink job reads via METADATA FROM 'value.headers.operation'
    Inserts into iceberg_orders_cdc_log (append-only)
  4. Iceberg commits new snapshot via Flink checkpoint (10s)
  5. dbt view mart_orders_cdc_current projects latest state per id
    ROW_NUMBER() OVER (PARTITION BY id ORDER BY event_ts DESC) WHERE rn=1 AND op <> 'DELETE'
  6. Athena query hits the view → sees order 1001 within seconds

End-to-end p95: ~5–10 seconds. No batch window, no second pipeline, no MERGE.

Pattern 1 — Basic streaming Kafka → Iceberg

sql/flink_kafka_to_iceberg.sql 
SET 'execution.runtime-mode'           = 'streaming';
SET 'execution.checkpointing.interval' = '10s';
SET 'execution.checkpointing.mode'     = 'EXACTLY_ONCE';

CREATE TABLE orders_stream (
  id STRING, customer_id STRING, order_ts TIMESTAMP(3),
  amount DECIMAL(10,2), status STRING
) WITH (
  'connector' = 'kafka',
  'topic'     = 'orders_topic',
  'properties.bootstrap.servers' = '${KAFKA_BOOTSTRAP_SERVERS}',
  'scan.startup.mode' = 'earliest-offset',
  'format'    = 'json'
);

CREATE CATALOG iceberg_catalog WITH (
  'type'         = 'iceberg',
  'warehouse'    = '${ICEBERG_WAREHOUSE_PATH}',
  'catalog-impl' = 'org.apache.iceberg.aws.glue.GlueCatalog',
  'io-impl'      = 'org.apache.iceberg.aws.s3.S3FileIO'
);

CREATE TABLE iceberg_catalog.`default`.iceberg_orders (...)
  WITH ('write.format.default' = 'parquet');

INSERT INTO iceberg_catalog.`default`.iceberg_orders
SELECT id, customer_id, order_ts, amount, status FROM orders_stream;

Use when: you only need latest state and don't care about update history.

Pattern 2 — CDC with Kafka headers (recommended)

sql/streaming_cdc_op_field.sql 
CREATE TABLE orders_cdc_with_headers (
  id STRING, customer_id STRING, order_ts TIMESTAMP(3),
  amount DECIMAL(10,2), status STRING,
  operation       STRING METADATA FROM 'value.headers.operation',
  source          STRING METADATA FROM 'value.headers.source',
  event_timestamp STRING METADATA FROM 'value.headers.timestamp',
  WATERMARK FOR order_ts AS order_ts - INTERVAL '0' SECOND
) WITH ( 'connector' = 'kafka', /* ... */ );

CREATE TABLE iceberg_catalog.`default`.iceberg_orders_cdc_log (
  id STRING, customer_id STRING, order_ts TIMESTAMP(3),
  amount DECIMAL(10,2), status STRING,
  operation STRING, source STRING, event_timestamp STRING,
  ingested_at TIMESTAMP(3)
);

INSERT INTO iceberg_catalog.`default`.iceberg_orders_cdc_log
SELECT id, customer_id, order_ts, amount, status,
       operation, source, event_timestamp, CURRENT_TIMESTAMP
FROM   orders_cdc_with_headers
WHERE  operation IS NOT NULL;

Use when: you need INSERT/UPDATE/DELETE history. Headers keep payload schema clean.

Pattern 3 — Streaming upsert with primary key

sql/streaming_upsert_primary_key.sql 
CREATE TABLE iceberg_catalog.`default`.iceberg_orders_upsert (
  id STRING,
  customer_id STRING,
  amount DECIMAL(10,2),
  status STRING,
  PRIMARY KEY (id) NOT ENFORCED
) WITH (
  'write.format.default'         = 'parquet',
  'format-version'               = '2',
  'write.upsert.enabled'         = 'true'
);

INSERT INTO iceberg_catalog.`default`.iceberg_orders_upsert
SELECT id, customer_id, amount, status FROM orders_stream;

Use when: you want Iceberg to handle deduplication itself (v2 row-level deletes). Higher write cost than append-only; benefits from PK-based pruning on read.

⚠ Tradeoff: small files multiply faster — schedule compaction more aggressively.

Pattern 4 — Soft delete (GDPR-friendly)

sql/streaming_soft_delete.sql + dbt/models/mart_orders_active.sql 
-- Flink: write all rows including is_deleted flag
CREATE TABLE iceberg_catalog.`default`.iceberg_orders_soft_delete (
  id STRING, customer_id STRING, amount DECIMAL(10,2),
  status STRING, is_deleted BOOLEAN
);

-- dbt: 5-line view selects only active rows
{{ config(materialized='view') }}
{{ soft_delete_active(
    source_table="iceberg_catalog.`default`.iceberg_orders_soft_delete",
    columns=['id', 'customer_id', 'order_ts', 'amount', 'status']
) }}

Use when: you need audit trail of deletions or can't hard-delete (regulatory). Pair with periodic purge job for true GDPR erasure.

Pattern 5 — Batch S3 → Iceberg backfill

sql/batch_s3_partitioned_parquet.sql 
SET 'execution.runtime-mode' = 'batch';

CREATE TABLE s3_orders_parquet (
  id STRING, customer_id STRING, order_ts TIMESTAMP(3),
  amount DECIMAL(10,2), status STRING,
  dt STRING -- partition column
) PARTITIONED BY (dt) WITH (
  'connector'  = 'filesystem',
  'path'       = 's3://my-bucket/raw/orders/',
  'format'     = 'parquet'
);

INSERT INTO iceberg_catalog.`default`.iceberg_orders
SELECT id, customer_id, order_ts, amount, status
FROM   s3_orders_parquet
WHERE  dt BETWEEN '2026-01-01' AND '2026-04-30';

Use when: backfilling history, replaying archived partitions, or recovering a corrupt streaming run. Same engine, same SQL — just execution.runtime-mode = batch.

dbt macro — the CDC projection

dbt/macros/cdc_current_state.sql 
{% macro cdc_current_state(source_table, key_columns, extra_columns,
                            order_column='event_ts',
                            op_column='op',
                            delete_value='DELETE') %}
SELECT {{ key_columns | join(', ') }},
       {{ extra_columns | join(', ') }},
       {{ op_column }} AS operation,
       {{ order_column }} AS last_modified_at
FROM (
  SELECT {{ key_columns | join(', ') }},
         {{ extra_columns | join(', ') }},
         {{ op_column }},
         {{ order_column }},
         ROW_NUMBER() OVER (PARTITION BY {{ key_columns | join(', ') }}
                            ORDER BY {{ order_column }} DESC) AS rn
  FROM {{ source_table }}
  WHERE {{ op_column }} <> '{{ delete_value }}'
)
WHERE rn = 1
{% endmacro %}

Adding a new CDC table = 5 lines

dbt/models/mart_customers_current.sql 
{{ config(materialized='view') }}

{{ cdc_current_state(
    source_table="iceberg_catalog.`default`.iceberg_customers_cdc_log",
    key_columns=['customer_id'],
    extra_columns=['name', 'email', 'tier']
) }}

Composite keys? Just pass a list:

key_columns=['tenant_id', 'customer_id']

Different op column? Override the default:

op_column='cdc_op', delete_value='D'

Result: no hand-written window functions, no SQL drift, no copy-paste bugs.

How the SQL Gateway runs on ECS

terraform/modules/ecs_sql_gateway/main.tf
  • Image: apache/flink:1.20.1-scala_2.12 + Iceberg/Glue/S3 jars baked in
  • Fargate task: 2 vCPU / 4 GB, taskmanager.numberOfTaskSlots: 4
  • Internal ALB on port 8083; health check GET /v1/info
  • Auto-scale 1–5 replicas on CPU > 60%
  • CloudWatch logs at /ecs/<team>/sql-gateway (7-day retention)
  • Task role grants: MSK IAM-SASL, S3 warehouse, Glue catalog
# Submit to the AWS gateway (same script, different env)
GATEWAY=http://${FLINK_GATEWAY_HOST}:8083 \
  ./scripts/run_sql_via_gateway.sh --file sql/streaming_cdc_op_field.sql

How dbt runs on a schedule

terraform/modules/ecs_dbt/
  • Image: Dockerfile.dbt — dbt-core 1.3.7 + dbt-flink-adapter 1.3.11
  • EventBridge Scheduler triggers ECS RunTask every ${dbt_schedule} (default 15 min)
  • Container env: DBT_TARGET=aws, FLINK_GATEWAY_HOST=<alb-dns>
  • Connects to gateway via internal ALB, submits compiled SQL via REST
  • Run results land in CloudWatch Logs; failures alarm via metric filter

Note: for streaming materializations, dbt run deploys jobs but doesn't manage their lifecycle — that's the next milestone (job registry + version-hash check).

Iceberg — what to know operationally

You get for free

  • ACID writes on S3
  • Schema evolution (add/drop/rename) without rewrites
  • Time travel by snapshot ID or timestamp
  • Hidden partitioning (no partition column maintenance)
  • Multi-engine reads (Flink, Trino, Athena, Spark)

You must operate

  • rewrite_data_files — compaction (small file problem)
  • expire_snapshots — bound metadata growth
  • remove_orphan_files — clean failed writes
  • Glue catalog access control (Lake Formation if multi-team)
-- Run periodically (Spark on EMR Serverless, or Flink batch)
CALL iceberg_catalog.system.rewrite_data_files('default.iceberg_orders_cdc_log');
CALL iceberg_catalog.system.expire_snapshots('default.iceberg_orders_cdc_log',
  TIMESTAMP '2026-04-01 00:00:00');

5 things that will bite you

  1. Small file problem. Streaming writes = thousands of tiny Parquet files. Compaction is not optional — schedule it from day one.
  2. Streaming job lifecycle. dbt deploys jobs, doesn't manage them. dbt run twice = two jobs unless you guard for it.
  3. Watermark misconfig. Late events get dropped silently. Always set WATERMARK FOR ts AS ts - INTERVAL '5' SECOND based on your producer's clock skew.
  4. Adapter version lock. dbt-flink-adapter is pinned to dbt-core 1.3.x. Don't bump dbt-core without checking adapter compatibility.
  5. Glue catalog rate limits. Heavy parallelism × Iceberg metadata = throttled Glue API calls. Cache catalog access in long-running jobs.
