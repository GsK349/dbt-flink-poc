02   /   SYSTEM OVERVIEW PART I — TOPOLOGY

01 / OVERVIEW

Two paths.
One destination.

Real-time events flow from Kafka through Flink-streaming into an immutable CDC log. Historical and bulk data flow from S3 Parquet through Flink-batch into target tables. Both land in the same Iceberg warehouse; dbt projects them into a single source of truth.

  • Streaming — long-lived, EXACTLY_ONCE, 10s checkpoints
  • Batch — one-shot, single commit, partition pruning
  • Iceberg — shared catalog, ACID, time-travel

03   /   STREAMING PIPELINE PART II — REAL-TIME CDC

PIPELINE A

Kafka → Flink → Iceberg log

The streaming pipeline appends every change-data event into an immutable CDC log. Operation type travels in the Kafka message header; Flink reads it as a virtual METADATA column and writes a flattened row per event.

  • Mode — runtime-mode = streaming
  • Checkpoint — every 10s, EXACTLY_ONCE
  • Sink — append-only Iceberg v2 table
  • Headers — operation, source, timestamp

04   /   BATCH PIPELINE PART III — BULK INGEST

PIPELINE B

S3 Parquet → Flink → Iceberg

Batch jobs read partitioned Parquet from S3 in parallel across TaskManagers. They run once, commit once. Partition pruning means a query against last week never touches last decade.

  • Mode — runtime-mode = batch
  • Layout — year=/month=/day= Hive-style
  • Commit — single snapshot at job end
  • Use cases — backfills, corrections, historical loads

06   /   DBT PROJECTION PART V — RESOLVING TRUTH

DOWNSTREAM

Log → truth.
One window at a time.

The CDC log is append-only — the same primary key may appear many times. dbt collapses each key to its latest event and filters out deletes, producing a single coherent current-state view. 

SELECT *
FROM (
  SELECT *,
    ROW_NUMBER() OVER (
      PARTITION BY id
      ORDER BY event_ts DESC
    ) AS rn
  FROM iceberg_orders_cdc_log
)
WHERE rn = 1
  AND op <> 'DELETE';

07   /   DBT × FLINK PART VI — THE INTEGRATION

ADAPTER LAYER

dbt compiles.
Flink executes.

The dbt-flink-adapter turns dbt's declarative SQL models into Flink SQL jobs against the SQL Gateway. Streaming and batch are the same code path — only a materialization config changes.

  • Compile — dbt parses Jinja, resolves ref(), builds DAG
  • Submit — adapter sends Flink SQL via SQL Gateway REST
  • Execute — Flink runs as streaming or batch
  • Materialize — view · table · incremental · streaming

08   /   STREAMING-AS-CODE PART VII — THE WORKFLOW

DEVELOPER LOOP

A streaming job is now a pull request.

Real-time pipelines used to live as imperative Java jars maintained by a platform team. Here, every transformation is a versioned dbt model — reviewed, tested, and deployed like any other change.

▸ BEFORE — JAVA JAR

Imperative Flink job. Maven build. Custom DSL. Platform team gatekeeps every change. New transformation = ticket + 2-week cycle.

▸ AFTER — DBT MODEL

Declarative SQL. Same workflow as warehouse models. Analyst can ship a streaming aggregation in an afternoon, lineage and tests included.

VALUE THESIS

One pipeline. Six superpowers.

Collapsing streaming and batch into a single dbt-managed surface unlocks capabilities that neither stack delivers alone. Each card below is a force-multiplier the PoC enables.

01 / UNIFIED
One SQL surface, two runtimes
The same dbt model can run as a long-lived stream or an overnight backfill — flip materialized and the adapter rewires the runtime. No code fork between Lambda and Kappa worlds.
02 / DEMOCRATISED
Analysts ship streaming
Anyone fluent in SQL can author a real-time pipeline. The platform team owns the runtime, not every transformation — removing the bottleneck on every new metric.
03 / GOVERNED
Lineage across both worlds
dbt's DAG now spans Kafka topics, CDC logs, batch tables and downstream marts. dbt docs renders one continuous map from source event to dashboard.
04 / TESTED
Data quality at the edge
unique, not_null, custom expectations — the same generic tests cover streaming sinks. Bad data fails the build, not the dashboard.
05 / RESILIENT
Replay without re-engineering

Iceberg + Parquet + Glue catalogue means Athena, Trino, Snowflake and Spark all read the same tables. Today Flink writes; tomorrow anything reads. No vendor moat.

10   /   CONFLICT №1 PART IX — THE UNDO PROBLEM

CONFLICT №1

When the stream undoes your fix.

A manual batch UPDATE on a streaming table is fragile — if Kafka replays the event, your fix is overwritten. The recommended pattern splits raw and clean tables.

▸ DANGER · single table

Streaming + manual UPDATE → race

Both writers target the same row. The last writer wins, and the stream usually wins last.

▸ SAFE · split tables

Raw (append) · Clean (manual) · View on top

The stream never touches the corrected table. dbt views read from _clean.

11   /   CONFLICT №2 PART X — GDPR × STREAMING

RIGHT TO ERASURE

Soft-delete now,
hard-delete later.

A hard DELETE during active streaming risks transaction conflicts. The pattern: streaming flips an is_deleted flag on the next event; a scheduled batch job purges flagged rows after the legal retention window. Every action lands in an immutable audit log.

  • Phase 1 — Soft · streaming sets is_deleted=TRUE
  • Phase 2 — Audit · request logged to deletion_audit
  • Phase 3 — Hard · batch DELETE WHERE is_deleted
  • Replay · Iceberg FOR SYSTEM_TIME AS OF '…' for compliance
